에이전트 기초

에이전틱 루프 : 추론 → 호출 → 관찰 반복

에이전트 구성요소 6가지 : 
Model
컨텍스트를 읽고 다음 행동을 결정하는 추론 엔진 — 에이전트의 두뇌
Tools
외부 시스템과 상호작용하는 인터페이스 — API, DB, 파일
Memory
대화 이력 + 장기 기억 — 컨텍스트 축적
Guardrails
행동 제한 — 금지 도구, 비용 한도, PII 차단
Context
시스템 프롬프트 + 대화 + 도구 결과
Orchestration
ReAct/ReWoo 루프 제어 + 멀티스텝 관리

같은 모델, 같은 SDK를 쓰는 두 팀의 에이전트 품질 차이는 결국 도구 설계와 상태 설계에서 갈립니다.

핵심 메커니즘 : ReAct, ReWoo
구분	ReAct	ReWoo
전략	매 스텝 판단	계획 먼저, 일괄 실행
LLM 호출	N회 (스텝마다)	2회 (계획 + 종합)
토큰 효율	낮음	높음 (HotpotQA 기준 최대 5배)
실행 시간	직렬 — 느림	병렬 — 빠름
적응력	✓ 높음 (중간 결과에 반응)	낮음 (계획 실패 시 재계획)
적합한 경우	대화형, HITL, 결과 의존성 높을 때	멀티도구, 병렬 가능, 비용 민감

도구 = 함수 + 도구 스키마
LLM은 코드를 읽지 못합니다 — name·description·inputSchema 설명서가 도구 선택의 유일한 근거입니다.

함수 — 실행되는 코드 (그대로)
python

def get_menu(restaurant_id: str) -> str:
    return db.fetch_menu(restaurant_id)

# 지금까지는 개발자가 직접 호출했음
menu = get_menu("R001")

도구 스키마 — LLM이 읽는 설명서 (JSON)
json

{
  "toolSpec": {
    "name": "get_menu",
    "description": "식당의 현재 메뉴와 가격 조회. 메뉴·가격 질문 시 호출.",
    "inputSchema": { "json": {
      "type": "object",
      "properties": {
        "restaurant_id": { "type": "string" }
      },
      "required": ["restaurant_id"]
    } }
  }
}

도구 스키마 3요소
LLM이 도구를 올바르게 선택하기 위한 필수 정보

name
동사+명사 패턴 — search_restaurants, get_weather, create_ticket

description
언제 쓰는지 + 입력 형식 + 반환값 — 도구 선택의 유일한 근거

inputSchema
required/optional 구분, 타입 제약, enum으로 입력 검증

@tool 데코레이터
스키마 3요소를 손으로 쓰지 않는 법 — Python 함수 자동 변환 (구현 예: Strands)

python

from strands import Agent, tool

# 1 도구 정의 — docstring이 LLM에게 전달되는 도구 설명
@tool
def search_restaurants(location: str, cuisine: str = None) -> str:
    """지역과 요리 종류로 식당을 검색합니다.

    사용자가 식당 추천을 요청할 때 호출하세요.
    location: 검색할 지역명 (예: "강남역")
    cuisine: 요리 종류 (예: "이탈리안"). 생략하면 전체 검색
    """
    return f"{location} 근처 식당 3곳 발견"

# 2 Agent에 도구 전달 → ReAct 루프에서 자율 호출
agent = Agent(
    model="us.anthropic.claude-sonnet-4-6",
    tools=[search_restaurants],
)

# 3 실행 — 모델이 스스로 도구 호출을 결정하고 결과를 종합
result = agent("강남역 이탈리안 추천해줘")
1
@tool 데코레이터 — 평범한 Python 함수가 그대로 도구가 됨. docstring·타입 힌트가 name·description·inputSchema로 자동 변환
2
tools=[...] 등록 — 모델이 선택할 수 있는 행동 목록. 리스트에 담는 순간 ReAct 루프의 선택지
3
실행 — 호출 여부·인자를 모델이 스스로 결정하고, Observation을 종합해 최종 답변

좋은 description 공식
"언제" + "뭘 넣고" + "뭘 받나" + "주의사항" — 길이가 아니라 판단 정보의 밀도

필수 요소
언제: "비용 금액/증감/추이 질문 시 호출"
입력: service — AWS 서비스명 (ec2, s3)
입력: period — 조회 기간 (last-7d)
출력: 일별 비용 데이터 (JSON)
주의: 서비스명 불명확하면 확인 후 호출

모델은 기억하지 않는다 — 매번 다시 읽는다
매 호출마다 messages[] 전체가 모델에 재전송됩니다 — session_id로 대화를 격리하고 인메모리 한계를 확인합니다.

세션과 session_id
대화 한 단위의 messages[] 묶음이 세션 — session_id는 그 묶음을 여는 열쇠

python

# 같은 session_id → 같은 messages[]를 이어받음 (개념 예)
chat(session_id="mina-conv1", "강남역 이탈리안 추천해줘")
chat(session_id="mina-conv1", "거기로 오늘 7시 예약해줘")
# → "거기" = 트라토리아 벨라 — 직전 턴이 같은 세션에 있음

chat(session_id="mina-conv2", "거기로 오늘 7시 예약해줘")
# → "거기"가 어디인가요? — 새 세션은 빈 messages[]에서 시작

chat(session_id="juno-conv1", "내 예약 보여줘")
# → mina의 대화와 완전 격리 — 다른 사용자, 다른 세션
1 세션 — 대화 한 단위로 묶인 messages[] — 저장·복원·격리의 기본 단위
2 session_id — 그 묶음을 찾는 키. 같은 id면 대화가 이어지고, 새 id면 처음부터
3 격리 — 사용자·대화가 다르면 id도 달라야 함 — 섞이면 남의 맥락이 흘러듦

에이전트 상태 vs 호출 컨텍스트
둘 다 모델에는 안 보이는 존재 — 수명과 주입 방향의 차이 (Strands: agent.state · agent.state)

에이전트 상태 - agent.state
세션 전체 유지
도구·훅이 읽고 쓰는 내부 저장소
세션 동안 여러 턴에 걸쳐 유지
세션 스토어가 함께 영속화
용도: 인증 토큰, 호출 카운터, 도구 간 공유 데이터
vs
호출 컨텍스트 - agent.state
1턴만 유효
호출자(caller)가 외부에서 주입
호출 시 파라미터로 함께 전달
저장 안 됨 — 매 호출마다 재주입
용도: API 키, user_id, 역할(role), 세션 비밀

모델이 보는 것 vs 못 보는 것
LLM에 노출되면 안 되는 민감 정보는 호출 컨텍스트로

상태	LLM이 봄?	도구/훅 접근?	용도
messages[]	✓ 매번 전체 전송	✓	대화 맥락 유지
에이전트 상태	✗	✓ 읽기/쓰기	도구 간 내부 데이터
호출 컨텍스트	✗	✓ 실행 컨텍스트로 접근	외부 주입 비밀/설정

세션 너머 — 장기 기억
세션이 끝나도 남아야 하는 기억의 조감 — 수명 3계층의 마지막 층

세션의 끝이 기억의 끝은 아니다
대화에서 남길 것을 추출해 저장하고, 다음 세션이 시작될 때 회수해 컨텍스트에 주입합니다.

장기 기억의 동작 원리
추출 → 저장 → 회수 → 주입 — 세션과 세션을 잇는 네 단계

기억의 세 종류와 남길 것
무엇을 남기는가 — 사실 · 선호 · 에피소드

사실 (Semantic)
"미나의 회사는 강남역 근처" — 잘 변하지 않는 정보

선호 (Preference)
"창가 자리 선호 · 매운 음식 못 먹음"

에피소드 (Episodic)
"7/20 트라토리아 벨라 예약 — 만족" — 과거 사건의 요약

에이전트 프롬프트 설계
시스템 프롬프트 구조부터 추론 모드 유도까지 — 답변이 아니라 행동을 설계하는 관점

좋은 답변이 아니라 올바른 행동
에이전트 프롬프트는 도구 선택과 실행을 지배합니다 — 4블록 구조와 역할 분담, 추론 모드 유도가 행동 품질을 결정합니다.

시스템 프롬프트 4블록 구조
에이전트가 올바르게 행동하도록 하는 설계 구조

python

# 시스템 프롬프트 4블록 — 역할·규칙·형식·제한
"""
## 1 역할 (Role)
당신은 AWS 비용 분석 전문가입니다.
도구를 사용하여 정확한 데이터 기반으로 답변합니다.

## 2 행동 규칙 (Rules)
- 비용 데이터 필요 → get_cost_data 먼저 호출
- 추측 금지 — 항상 도구 결과 기반
- 한 번에 도구 3개 이상 연속 호출 금지

## 3 출력 형식 (Format)
- 금액: USD, 소수점 2자리
- 증감률: 퍼센트
- 요약 먼저, 상세 나중에

## 4 제한 (Constraints)
- 비용 최적화 "실행"은 금지 (분석과 제안만)
- 다른 계정 접근 금지
"""
1역할 — 정체성 + 행동 방침. "도구로 데이터 기반 답변"까지 역할에 포함
2행동 규칙 — 도구 사용 순서·추측 금지·호출 횟수 제한. 오동작 시 가장 먼저 손볼 블록
3출력 형식 — 단위·자릿수·서술 순서를 고정해 응답 일관성 확보
4제한 — 권한의 경계. 못 하게 할 일(실행 금지·계정 접근 금지)을 명시

시스템 프롬프트 vs 도구 description
행동 규칙과 도구 선택 근거 — 무엇을 어디에 쓰나

설계 요소	어디에	이유
역할 · 행동 규칙 · 제한	시스템 프롬프트	에이전트 전체 — 모든 턴에 적용
출력 형식 (단위 · 순서)	시스템 프롬프트	응답 일관성 — 전역 규칙
"언제 이 도구를 쓰나"	도구 description	도구 선택의 근거 — 도구 단위
파라미터 의미와 형식	도구 description + inputSchema	입력 검증 — 스키마와 함께

from strands import Agent
from strands.tools.mcp import MCPClient
from mcp import stdio_client, StdioServerParameters

# 1 MCP 클라이언트 — transport callable로 stdio 서버 연결
mcp = MCPClient(lambda: stdio_client(StdioServerParameters(
    command="npx",
    args=["-y", "@modelcontextprotocol/server-filesystem", "/tmp"],
)))

# 2 연결 컨텍스트 — 서버 도구를 로드해 에이전트에 등록
with mcp:
    agent = Agent(
        tools=mcp.list_tools_sync(),  # 3 MCP 서버 도구 자동 등록
    )
    result = agent("/tmp 디렉토리의 파일 목록을 보여줘")

from pydantic import BaseModel

# 1 선언 — 클래스 필드의 타입 힌트가 곧 규격

    time: str

Reservation.model_json_schema()

from strands import Agent

# 출력 스키마 정의 — Pydantic 모델이 곧 JSON Schema

    price_won: int

세션 저장과 복원
session_id 하나로 전체 대화 상태를 영속화·복원

python

from strands import Agent
from strands.session import S3SessionManager

# 1 장착 — session_id + S3 버킷으로 저장 위치 지정
agent = Agent(session_manager=S3SessionManager(
    session_id="user-123-reservation",
    bucket="agent-sessions-bucket",
))
agent("강남에 오늘 저녁 2명 예약 가능한 이탈리안 찾아줘")

# 2 복원 — 같은 session_id로 재생성하면 이전 대화 자동 로드
agent2 = Agent(session_manager=S3SessionManager(
    session_id="user-123-reservation",
    bucket="agent-sessions-bucket",
))
agent2("아까 찾은 곳 중 트라토리아 벨라로 예약해줘")  # 3
1
장착 한 줄로 저장 자동 — save()를 호출하지 않음, 매 턴 messages[]와 agent.state가 함께 영속화
2
복원 키는 session_id — 같은 ID로 Agent를 다시 만들면 이전 대화가 그대로, S3 백엔드는 파일시스템 없는 Lambda·Fargate에서도 유지
3
이전 턴의 검색 결과를 기억한 채 이어서 응답 — 브라우저 새로고침·서버 재시작에도 대화가 계속

messages[] 밖의 상태 — agent.state
모델에게는 보이지 않지만, 세션과 함께 저장되는 key-value 상태

핵심 포인트
agent.state
대화 밖 key-value 저장소 — 모델 컨텍스트에 전송되지 않음
set / get
카운터·플래그·사용자 메타데이터를 코드에서 직접 읽고 씀
영속화
SessionManager가 messages[]와 함께 저장·복원
용도
멤버 등급·예약 횟수·중간 결과처럼 모델이 몰라도 되는 값
코드
python

from strands import Agent
from strands.session import FileSessionManager

mgr = FileSessionManager(session_id="user-123")
agent = Agent(session_manager=mgr)

# 모델 컨텍스트에 들어가지 않는 key-value 상태
agent.state.set("member_grade", "vip")
agent.state.set("reservation_count", 3)
print(agent.state.get("member_grade"))  # "vip"

# 세션 저장소에 messages[]와 함께 영속화 — 재생성해도 유지
agent2 = Agent(session_manager=FileSessionManager(session_id="user-123"))
print(agent2.state.get("reservation_count"))  # 3

1턴짜리 주입 상태 — invocation_state
호출할 때마다 밖에서 넣는 파라미터 봉투 — agent.state와 수명·방향이 다른 짝

핵심 포인트
invocation_state
호출 파라미터로 주입하는 1턴짜리 상태 — 저장되지 않고 매 호출 재주입
접근
도구·훅에서 tool_context.invocation_state — 모델 컨텍스트에는 안 들어감
agent.state와 차이
수명(세션 vs 1턴)과 방향(내부에서 축적 vs 외부에서 주입)
용도
API 키 · user_id · 역할 — 호출자만 아는 비밀과 설정
코드
python

from strands import Agent

agent = Agent(

4
분산 협업 패턴
