# 코드 리뷰와 리팩토링

## 원칙

**리뷰는 "고칠 것 찾기"가 아니라 "고칠 가치가 있는 것 찾기"다.**
지적 개수가 리뷰 품질이 아니다. 실제로 문제를 일으키는 것과,
스타일 취향 차이를 명확히 구분해서 보고한다.

**근거 없는 지적을 하지 않는다.** "일반적으로 이렇게 합니다"는 근거가
아니다. 이 코드에서 실제로 무엇이 깨지는지, 또는 어떤 상황에서 깨질지
말할 수 있어야 지적이다. 확인하지 않았으면 확인하지 않았다고 말한다.

## 우선순위

높은 것부터 본다. 아래로 갈수록 "고치지 않아도 되는" 쪽이다.

### 1순위 — 동작 실패 (반드시 고침)

실제로 재현되는 버그. 지적할 때는 **재현 방법과 결과를 함께 제시**한다.

- 잘못된 로직, 예외 미처리, 리소스 누수
- 실행 환경 의존성 (경로, cwd, 환경변수 가정)
- 특정 조건에서만 터지는 경계 조건

### 2순위 — 보안·비밀 노출 (반드시 고침)

- 자격 증명, 토큰, 계정 ID 하드코딩
- 공개 리포에 올라가면 안 되는 값이 `.gitignore`에 없는 상태
- 인증 없이 외부에 노출되는 엔드포인트
- 로그·에러 메시지에 민감 정보 유출

### 3순위 — 재현성 (대체로 고침)

- 의존성 버전 미고정
- 환경별 값이 코드에 박혀 다른 환경에서 실행 불가
- 실행 순서·사전 조건이 문서화되지 않음

### 4순위 — 가독성·구조 (선택)

- 이름이 역할을 설명하지 못함
- 함수가 너무 많은 일을 함
- 중복 코드

### 5순위 — 스타일 (거의 안 고침)

포매터·린터가 자동으로 처리할 수 있는 것은 사람이 지적하지 않는다.

## 리팩토링하지 않는 게 맞는 경우

리팩토링을 제안하기 전에 아래를 확인한다. 해당하면 **그대로 두는 것이
정답**이고, 그 판단 근거를 밝힌다.

**교육·학습용 코드에서 파일 간 독립성이 중요할 때**
공통 모듈로 빼면 독자가 두 파일을 왔다갔다 해야 한다. 3~5줄짜리
유틸 함수의 중복은 독립적으로 읽히는 가치보다 작다.

**중복이 우연이고 함께 변하지 않을 때**
같아 보이지만 서로 다른 이유로 존재하는 코드는 합치면 나중에
한쪽만 바꿔야 할 때 문제가 된다.

**앞으로 확장되지 않을 코드일 때**
일회성 스크립트, 실습 기록용 코드에 추상화 레이어를 넣으면
읽기만 어려워진다.

**동작을 검증할 방법이 없을 때**
회귀 테스트 없이 하는 리팩토링은 리팩토링이 아니라 도박이다.
먼저 검증 수단을 만들거나, 손대지 않는다.

## 리팩토링 절차

1. **검증 수단 확보** — 테스트가 있으면 실행해서 통과를 확인한다.
   없으면 최소한 스크립트를 실행해 현재 동작(출력·종료 코드)을 기록한다.
2. **한 번에 하나만** — 여러 종류의 변경을 섞지 않는다.
   경로 수정과 함수 분리를 같이 하면 무엇이 깨졌는지 알 수 없다.
3. **각 변경 후 검증** — 1번에서 기록한 동작이 유지되는지 확인한다.
4. **커밋 분리** — 리팩토링 커밋과 기능 변경 커밋을 섞지 않는다
   (`refactor:` vs `feat:`).

## 보고 형식

리뷰 결과는 이렇게 정리한다.

```
## 반드시 고칠 것
- [재현됨] <문제> — <재현 방법>, <실제 결과>
  → <수정 방향>

## 고치면 좋은 것
- <문제> — <어떤 상황에서 문제가 되는지>

## 그대로 두는 게 맞는 것
- <항목> — <왜 두는지>

## 확인하지 못한 것
- <항목> — <왜 확인 못했는지>
```

마지막 두 섹션을 생략하지 않는다. "안 고쳐도 되는 이유"와
"확인 못 한 범위"를 밝히는 것이 리뷰의 신뢰도를 만든다.

## 공개 전 최종 점검

리포를 public으로 만들거나 push하기 전:

```bash
git add -n .                      # 무엇이 올라가는지 확인
grep -rn "AKIA\|ASIA" --exclude-dir=.venv* .   # 액세스 키 패턴
grep -rn "<계정ID 12자리>" --exclude-dir=.venv* .
```

- `.gitignore`가 자격 증명·환경별 설정 파일을 덮는지 확인
- 스크립트를 리포 루트에서 실행해 경로 의존성 확인
- README의 실행 방법이 실제로 동작하는지 확인
