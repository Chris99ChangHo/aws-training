# Strands Agents SDK 설계 가이드

## 이 문서를 쓰는 방식

**API 시그니처, 클래스명, 파라미터는 이 문서에 적지 않는다.**
Strands는 거의 매주 릴리스되므로(Python Harness는 2026-07 기준 v1.50.x)
정적 문서에 API를 적으면 빠르게 낡는다.

코드를 쓰기 전에 반드시 실제 문서를 확인한다. 우선순위:

1. **MCP 서버** — `strands-agents` MCP의 `search_docs` / `fetch_doc`
   (`~/.kiro/settings/mcp.json`에 설정되어 있음)
2. **llms.txt** — `https://strandsagents.com/llms.txt` (문서 색인)
   / `llms-full.txt` (전문)
3. **API 레퍼런스** — `https://strandsagents.com/docs/api/python/<모듈>/index.md`

기억에 의존해 API를 작성하지 않는다. 확인하지 않았으면 확인하지 않았다고
말한다.

## 핵심 개념

Strands는 **model-driven** 접근을 취한다. 워크플로를 사람이 하드코딩하는
대신, 세 가지를 주고 모델이 스스로 판단하게 한다.

1. **모델** (LLM)
2. **시스템 프롬프트**
3. **도구 집합**

에이전트 루프가 추론 → 도구 호출 → 관찰을 반복하며 목표에 도달한다.
따라서 "어떤 순서로 실행할지"를 코드로 짜기보다, **도구를 잘 설계하고
프롬프트로 의도를 전달하는 것**이 핵심 작업이 된다.

## 멀티 에이전트 패턴 선택

단일 에이전트로 되는 일은 단일 에이전트로 한다. 나누는 것 자체가
비용(토큰, 지연, 디버깅 난이도)이다. 나눠야 할 때 아래에서 고른다.

| 패턴 | 언제 쓰는가 | 제어 수준 |
|---|---|---|
| **agents-as-tools** | 오케스트레이터가 도메인 전문 에이전트에게 위임. 계층 구조가 자연스러울 때 | 중간 |
| **swarm** | 에이전트들이 자율적으로 핸드오프하며 협업. 누가 다음에 일할지 미리 정할 수 없을 때 | 낮음 |
| **graph** | 실행 순서를 DAG나 순환으로 명시하고 싶을 때. 조건 분기 필요 | 높음 |
| **workflow** | 순차적 단계가 명확하고 단계 간 컨텍스트를 넘길 때 | 높음 |
| **A2A** | 다른 플랫폼/원격에 있는 에이전트와 연결할 때 | — |

판단 기준: **결정론이 필요한 만큼만 제어를 높인다.** 순서를 반드시
지켜야 하면 graph/workflow, 모델의 판단에 맡기는 게 나으면 swarm.

## 도구 설계

- 도구는 **하나의 명확한 동작**을 하게 만든다. 여러 일을 하는 도구는
  모델이 언제 쓸지 판단하기 어려워진다.
- 도구 이름과 docstring이 곧 모델에게 주는 설명서다. 인자 의미와
  반환 형태를 docstring에 정확히 쓴다.
- 부작용이 큰 도구(삭제, 결제, 외부 전송)는 승인 게이트를 둔다
  (hooks 또는 interventions로 가로챈다).
- 도구 결과가 지나치게 크면 컨텍스트를 잡아먹는다. 이 문제를 위한
  전용 플러그인이 있으니 문서에서 `context-offloader`를 확인한다.

## 관측·제어 지점

동작을 가로채거나 관찰할 수단이 여러 층으로 있다. 목적에 맞게 고른다.

- **hooks** — 에이전트 루프의 각 단계(모델 호출 전후, 도구 호출 전후)에
  개입. 로깅·검증·차단에 쓴다.
- **interventions** — 인가, 가드레일, 스티어링을 위한 상위 제어 계층.
  타입 있는 액션과 순서 있는 평가를 제공한다.
- **plugins** — 재사용 가능한 확장 단위. 스티어링, 컨텍스트 관리 등.
- **telemetry** — OpenTelemetry 기반 트레이스·메트릭.

간단한 로깅이면 hooks, 정책 기반 차단이면 interventions를 먼저 본다.

## 모델 프로바이더 선택

- **Amazon Bedrock** — AWS 환경이면 기본 선택. IAM으로 인증하고
  가드레일·프롬프트 캐싱을 함께 쓸 수 있다.
- 그 외 Anthropic API, OpenAI, Gemini, Ollama(로컬), LiteLLM(다중),
  SageMaker 등을 지원한다. **에이전트 코드를 바꾸지 않고 교체 가능**하도록
  설계되어 있으므로, 초기에 프로바이더를 고민하는 데 시간을 쓰지 않는다.

## 컨텍스트 관리

대화가 길어지면 토큰 한도에 부딪힌다. 선택지:

- **sliding window** — 오래된 메시지를 버린다. 단순하고 예측 가능.
- **summarizing** — 오래된 대화를 요약해 유지한다. 맥락 보존이 중요할 때.
- **session manager** — 세션 간 대화를 영속화(파일, S3 등).
- **memory store** — 세션을 넘어 사실을 장기 기억. Bedrock Knowledge Base를
  백엔드로 쓸 수 있다.

"대화 이어가기"는 session manager, "이전에 알게 된 사실 기억하기"는
memory store다. 둘을 혼동하지 않는다.

## 배포 대상 선택

| 대상 | 적합한 경우 |
|---|---|
| **Bedrock AgentCore Runtime** | 서버 관리 없이 세션 격리된 에이전트 실행. AWS 관리형 선호 시 |
| **AWS Lambda** | 짧은 요청·응답, 간헐적 트래픽, 비용 최소화 |
| **Fargate / App Runner** | 스트리밍 응답이 필요한 상시 서비스 |
| **EKS / EC2** | 기존 인프라에 통합하거나 세밀한 제어 필요 |
| **Docker (로컬)** | 배포 전 검증 |

Lambda는 실행 시간·스트리밍 제약이 있으니, 장시간 추론이나 토큰 스트리밍이
필요하면 Fargate 계열을 먼저 검토한다.

## 안전

- 도구에 **최소 권한**만 준다. 에이전트가 쓸 수 있는 것이 곧 공격 표면이다.
- 사용자 입력이 프롬프트에 들어가면 프롬프트 인젝션을 가정하고 설계한다.
  도구 인자를 검증하고, 외부 콘텐츠의 지시를 따르지 않도록 프롬프트에
  명시한다.
- 텔레메트리에 PII가 흘러가지 않게 한다.
- 프로덕션 전에 평가를 돌린다. Strands Evals SDK에 도구 선택 정확도,
  환각 탐지, 레드팀 등 평가기가 있다.
