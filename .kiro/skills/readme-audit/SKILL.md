# README 표준 점검과 보완

## 원칙

**표준은 `repo-structure.md`에 있다.** 이 스킬은 그 표준을 어떻게
검사하고, 무엇이 빠졌을 때 어떻게 채우는지에 대한 절차다. 표준
자체를 바꾸려면 스킬이 아니라 `repo-structure.md`를 수정한다.

**빠진 걸 만들어 채우지 않는다.** 트러블슈팅, 검증 결과, 비용
주의사항 같은 항목은 실제로 있었던 사실을 근거로 써야 한다. 근거가
없으면 "확인 필요"로 남기고 사용자에게 물어본다. 그럴듯한 문장을
지어내는 것은 포트폴리오 신뢰도를 해친다.

## 점검 대상

1. **최상위 `README.md`** — 과정 목록 표가 실제 `<과정명>/` 폴더와
   일치하는지 (새 과정 폴더가 생겼는데 표에 없거나, 반대의 경우).
2. **과정 `README.md`** (`<과정명>/README.md`) — 실습 목록 표가 실제
   `<실습명>/` 폴더와 일치하는지.
3. **실습 `README.md`** (`<과정명>/<실습명>/README.md`) — 아래
   체크리스트 전체.

## 실습 README 체크리스트

`repo-structure.md`의 "실습 README에 담을 것" 6개 항목을 순서대로
확인한다.

| 항목 | 확인할 것 |
|---|---|
| 1. 기술 배지 | 제목 바로 아래에 shields.io 정적 배지가 있는가. 실제 `requirements.txt`·코드에서 쓴 기술과 배지가 일치하는가 (안 쓰는 기술 배지가 남아있거나, 쓴 기술이 빠지지 않았는가). |
| 2. 아키텍처 | 텍스트 다이어그램(또는 그림)이 있는가. 코드의 실제 흐름과 맞는가. |
| 3. 설계 결정·트러블슈팅 | "됐다/안 됐다"가 아니라 원인 분석 과정이 있는가. 없으면 커밋 히스토리·코드 주석에서 근거를 찾아보고, 없으면 사용자에게 물어본다. |
| 4. 실행 방법 | 실제로 명령어를 실행해서 문서대로 동작하는지 확인한다 (가능한 경우). |
| 5. 검증 결과 | 수치·비교표가 있는가, 아니면 "됐음"으로만 끝나는가. |
| 6. 비용 주의사항 | 상시 과금 리소스(KB, 컴퓨트 등)가 있는데 명시가 없는가. |

## 절차

1. **스캔** — 대상 폴더의 README와 실제 코드/구조를 함께 읽는다.
   README만 보고 판단하지 않는다 (예: "아키텍처"가 실제 코드 구조와
   다르게 서술되어 있을 수 있다).
2. **격차 보고** — 항목별로 아래 형식으로 보고한다. 사용자 승인 전에
   파일을 먼저 고치지 않는다.
   ```
   ## <실습 폴더명>

   - [빠짐] <항목> — <무엇이 없는지>
   - [불일치] <항목> — <문서와 실제가 다른 지점>
   - [근거 필요] <항목> — <채우려면 사용자에게 물어야 하는 것>
   ```
3. **보완** — 사용자가 승인한 항목만 수정한다. 기술 배지처럼 코드에서
   기계적으로 확인 가능한 항목은 바로 고쳐도 되지만, 트러블슈팅·설계
   결정처럼 서술이 필요한 항목은 사용자가 준 사실을 그대로 반영한다.
4. **최상위·과정 README 동기화** — 실습 폴더를 새로 추가하거나 이름을
   바꿨다면 상위 README의 표도 함께 갱신한다.

## 기술 배지 갱신 시 주의

- 새 배지를 추가할 때 로고는 [simple-icons](https://simpleicons.org/)
  slug를 실제로 검색해서 존재하는 slug인지 확인한다. 추측한 slug는
  깨진 이미지로 나온다.
- 버전 표기(`Python-3.12`)는 실제 `requirements.txt`나 실행 환경의
  버전과 맞춘다. 임의로 넣지 않는다.
