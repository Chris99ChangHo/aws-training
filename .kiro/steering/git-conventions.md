# Git 작성 규칙

기본은 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/)을
따른다.

## 커밋 메시지 형식

```
<type>(<scope>): <subject>

<body>
```

- `type`: 아래 표 참고. 필수.
- `scope`: 변경 범위. 이 리포에서는 과정 폴더명 또는 실습명
  (예: `genai-essentials`, `seoul-travel-kb`). 생략 가능.
- `subject`: 영문 명령형, 첫 글자 소문자, 마침표 없음, 50자 이내.
- `body`: 필요할 때만. 무엇을 바꿨는지보다 **왜 바꿨는지**를 쓴다.
  한글로 써도 된다.

| type | 용도 |
|---|---|
| `feat` | 새 기능·새 실습 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서·README·이론 노트 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `test` | 테스트 추가·수정 |
| `chore` | 설정, 의존성, 빌드 등 부수 작업 |

예시:

```
feat(genai-essentials): add hybrid search comparison script

시맨틱 검색만으로는 문서 고유 키워드가 있는 질의에서 재현율이 낮아
overrideSearchType=HYBRID 비교 스크립트를 추가함.
```

## 커밋 단위

- 하나의 커밋은 하나의 논리적 변경만 담는다.
- 리팩토링과 기능 추가를 같은 커밋에 섞지 않는다.
- 실습 하나를 완성했으면 그 단위로 커밋한다.

## 브랜치

- 기본 브랜치는 `main`.
- 혼자 작업하는 학습 리포에서는 `main`에 직접 커밋해도 무방하다.
- 실험적인 큰 변경은 브랜치를 따고 진행한다.

## 커밋 전 안전 점검

**공개 리포이므로 커밋 전에 반드시 확인한다.**

### 1. 스테이징 대상을 눈으로 확인

```bash
git add -n .        # 실제로 추가하지 않고 목록만 출력
git status --short  # add 후 상태 확인
```

`git add .`를 습관적으로 치지 말고, 무엇이 올라가는지 먼저 본다.

### 2. 절대 커밋하지 않는 것

- AWS 자격 증명 (`credentials`, `*.pem`, `*.key`, 액세스 키 문자열)
- AWS 계정 ID (12자리 숫자)
- 환경별 리소스 식별자 (KB ID, 데이터소스 ID, 버킷명 등)
  → 이 리포에서는 `kb_info.json`이 해당. `.gitignore`로 제외되어 있다.
- 가상환경(`.venv*/`), `__pycache__/`, `.DS_Store`
- 개인 이메일이 노출되는 git config
  (`<username>@users.noreply.github.com` 사용 권장)

### 3. 스크린샷을 첨부할 때

콘솔 캡처를 리포에 넣을 경우, 이미지에서 아래를 가린다:

- 계정 ID, ARN 전체 경로
- KB ID·버킷명 등 리소스 식별자
- 로그인 사용자명·이메일 (콘솔 우측 상단)

리전명, 서비스명, 정책 구조, 검색 결과 화면은 가릴 필요 없다 —
오히려 실습 내용을 보여주는 데 도움이 된다.

**주의**: 워크숍 리소스가 나중에 삭제되어도 **캡처 이미지에 박힌 ID는
영구히 남는다.** 지우기 전에 가려야 한다.

### 4. 이미 커밋한 뒤 민감 정보를 발견했다면

`git rm --cached`로 지우고 다시 커밋해도 **히스토리에는 남는다.**
public 리포라면 노출된 자격 증명은 즉시 폐기·교체하고,
필요하면 히스토리 재작성(`git filter-repo`)을 고려한다.
