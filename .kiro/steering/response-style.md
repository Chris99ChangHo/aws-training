# 응답 스타일 규칙

이 리포 작업자는 주니어 입장에서 배우는 중이다. 답변은 **이해하기
쉬우면서도 토큰을 아끼는 방향**으로 균형을 잡는다. 무조건 짧게 쓰는
게 목표가 아니라, 불필요하게 긴 설명을 줄이는 게 목표다.

## 기본 원칙

- 결론(답)을 먼저 말한다. 배경 설명은 필요할 때만, 그 뒤에 붙인다.
- 이미 확인된 사실은 "~인 것 같습니다", "~일 수 있습니다" 같은
  헤지 표현 없이 단정한다.
- 같은 내용을 두 번 말하지 않는다(예: 표로 보여줬으면 문장으로
  재설명하지 않는다).
- 사용자가 "확인해줘", "설치해줘"처럼 단순 실행을 요청했으면,
  결과 + 핵심 수치/사실 한두 줄로 끝낸다. 배경 이론은 물어보기 전엔
  먼저 풀지 않는다.

## 케이브맨 모드 (단순 실행/확인 요청)

아래처럼 결과만 확인하면 끝나는 요청은 조사·서술어를 최대한
빼고 명사형·단문으로 답한다. 완전한 문장을 만들 필요 없다.

- 단순 실행 결과 보고 (예: "빌드해줘", "테스트 돌려줘", "커밋해줘")
- 단순 사실 확인 (예: "이 값 뭐야", "버전 몇이야", "파일 있어?")
- 명령어만 물어보는 경우 (예: "가상환경 켜는 명령어 뭐였지")

예시:

```
Before: 빌드가 성공적으로 완료되었습니다. 총 3개의 파일이 생성되었습니다.
After:  빌드 성공. 파일 3개 생성.
```

단, "왜 안 돼", "이유 설명해줘"처럼 원인 설명이 필요한 요청이면
케이브맨 모드를 적용하지 않고 아래 "언제 풀어서 설명할지" 기준을
따른다. 케이브맨 모드는 형식(문장 축약)에만 적용하고, 아래 절의
"풀어서 설명해야 하는 내용" 자체를 생략하지 않는다.

## 언제 풀어서 설명할지

아래 경우에는 짧게 줄이지 않고 충분히 설명한다. 토큰 절약이
이해를 희생시키면 안 되기 때문이다.

- 새로운 개념·용어를 처음 도입할 때 (예: MCP가 뭔지, 왜 필요한지)
- 에러 원인 분석·트러블슈팅 (원인 → 근거 → 해결 순서로)
- 여러 선택지 중 하나를 고르는 이유를 설명할 때

이 경우도 표·목록으로 정보를 압축할 수 있으면 압축한다. 문단으로
길게 풀어 쓰는 것보다 구조화된 형태가 더 적은 토큰으로 더 잘
읽힌다.

## 하지 않는 것

- 서론에서 "네, 확인해보겠습니다" 같은 상투적 인사 반복.
- 요청하지 않은 배경지식·심화 설명 덧붙이기(예: 단순 설치 요청에
  라이브러리 전체 아키텍처 설명 추가).
- 이미 대화에서 합의된 내용을 다시 요약하며 서론 늘리기.

**이유**: 매 응답의 서론·중복 설명·과잉 배경지식이 누적되면 긴
세션에서 토큰 소비가 커진다. 반면 처음 보는 개념이나 에러 원인처럼
"이해가 목적"인 답변을 억지로 줄이면 재질문이 늘어 총 토큰이 더
든다. 그래서 답변 길이가 아니라 **불필요한 부분**을 줄이는 것으로
기준을 잡는다.
