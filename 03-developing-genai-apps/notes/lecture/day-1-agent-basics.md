## 1. 체인 vs 에이전트

`[해석]` 두 방식의 갈림길은 하나다 — **실행 경로를 미리 그릴 수 있는가.**

- 경로가 고정되어 있으면(항상 A → B → C 순서) **체인**으로 충분하다. 모델은
  각 단계의 출력만 만들고, 순서 자체는 코드가 결정한다.
- 경로가 입력에 따라 달라지면(때로는 A만, 때로는 A → C → B) 그 판단을 모델에
  맡기는 **에이전트**의 자율성이 값을 갖는다.

`[해석]` 이 구분은 "에이전트가 더 발전된 방식"이라는 뜻이 아니다. 경로가
고정된 작업에 에이전트를 쓰면 불필요한 판단 단계가 늘어 지연·비용·오류
가능성이 커진다. 체인으로 충분한 문제는 체인으로 푼다.

## 2. 에이전트를 이루는 6가지 구성요소

`[해석]` 프로덕션 에이전트는 다음 6가지로 분해된다.

| 구성요소 | 역할 |
|---|---|
| Model | 컨텍스트를 읽고 다음 행동을 결정하는 추론 엔진 |
| Tools | 외부 시스템과 상호작용하는 인터페이스 (API, DB, 파일) |
| Memory | 대화 이력 + 장기 기억 — 컨텍스트 축적 |
| Guardrails | 행동 제한 — 금지 도구, 비용 한도, PII 차단 |
| Context | 시스템 프롬프트 + 대화 + 도구 결과 (RAG 결과도 여기 포함) |
| Orchestration | ReAct/ReWoo 같은 루프 제어 + 멀티스텝 관리 |

`[해석]` 여기서 **Model을 뺀 나머지 다섯 개가 "하네스"**다. 하네스는 결국
"모델이 스스로 하지 못하는 일을 대신 해주는 도구들의 집합"으로 볼 수 있다 —
모델은 추론만 하고, 그 추론을 실제 행동·기억·제약으로 옮기는 배선이 하네스다.
"프롬프트 → 컨텍스트 → 하네스"로 이어지는 최근 흐름은, 관심의 초점이
프롬프트 한 줄 최적화에서 모델을 둘러싼 시스템 설계로 이동하고 있다는 뜻으로
읽을 수 있다.

## 3. 자율성 3단계

`[해석]` AI가 실행 권한을 얼마나 갖는지에 따라 3단계로 나눈다.

| 단계 | 실행 주체 | 특징 |
|---|---|---|
| 1. AI Assistant | 사람 | AI는 답변·제안까지만, 실행은 사람 (챗봇, 인라인 코드 제안) |
| 2. AI Agent | AI | 목표를 위임받아 도구를 호출하고 결과를 판단해 실행까지 완료하는 단일 에이전트. 권한 위임이 시작되는 지점이므로, 고위험 동작 앞에는 승인 게이트(Human-in-the-Loop)를 둔다 |
| 3. Agentic AI | AI | 시스템 수준 자율 — 멀티 에이전트 협업, 여러 날에 걸친 태스크, 자기 검증까지 포함 |

`[해석]` 단계가 올라갈수록 자율성과 함께 **실패의 파급 범위**도 커진다.
2단계부터는 "무엇을 자동 실행해도 되고 무엇은 승인이 필요한가"를 설계
단계에서 정해야 한다.

## 4. 핵심 메커니즘: ReAct vs ReWoo

`[문서]` ReWOO(Reasoning WithOut Observation)는 ReAct의 "매 스텝마다 관찰하고
다시 추론하는" 구조를 "먼저 전체 계획을 세우고 한꺼번에 실행"하는 구조로
바꾼 패턴이다. 논문은 HotpotQA(멀티홉 추론 벤치마크)에서 **토큰 소비 5배
감소, 정확도 4%p 향상**을 보고한다.
([Xu et al., 2023, arXiv:2305.18323](http://arxiv.org/abs/2305.18323))

| 구분 | ReAct | ReWoo |
|---|---|---|
| 전략 | 매 스텝 판단 | 계획 먼저, 일괄 실행 |
| LLM 호출 | N회 (스텝마다) | 2회 (계획 + 종합) |
| 토큰 효율 | 낮음 | 높음 (HotpotQA 기준 최대 5배, `[문서]`) |
| 실행 방식 | 직렬 — 느림 | 병렬 — 빠름 |
| 적응력 | 높음 (중간 결과에 반응) | 낮음 (계획이 틀리면 재계획 필요) |
| 적합한 경우 | 대화형, HITL, 결과 의존성이 높을 때 | 멀티도구, 병렬 가능, 비용에 민감할 때 |

`[해석]` ReWoo가 항상 더 좋은 것은 아니다 — 한 스텝의 결과가 다음 스텝의
방향을 바꿔야 하는 작업(예: "이 검색 결과가 비어 있으면 다른 방식으로
재검색")에는 ReAct의 적응력이 필요하다. ReWoo는 계획이 실행 전에 확정되므로
중간에 상황이 바뀌는 것을 반영하지 못한다.

## 5. 도구 스키마 3요소

`[해석]` 프로그래밍에서 함수는 수학의 함수와 달리 필요에 따라 새로 정의해서
쓰는 것이다. 예전에는 개발자가 함수를 정의하고 직접 호출했지만, 에이전트
방식에서는 **모델이 필요에 따라 호출 여부와 인자를 스스로 결정**한다. 다만
모델은 코드를 읽지 못하므로, 호출을 판단할 근거로 별도의 **도구 스키마**(JSON
형식의 설명서)가 필요하다.

좋은 도구 설계의 원칙:

- **단일 책임**: 도구 하나는 한 가지 일만 하도록 좁게 정의한다.
- **description을 구조적으로 작성**: "언제 쓰는지 + 무엇을 넣는지 + 무엇을
  반환하는지"가 도구 선택의 유일한 근거다. 모델은 코드를 보지 않는다.

일반 프롬프트와 에이전트 프롬프트의 차이도 결국 여기로 모인다 — 가장
중요한 것은 올바른 도구 선택과 그 근거가 되는 설명이고, **모르면 모른다고
답하게** 만드는 것이 대화가 꼬이지 않게 하는 핵심이다.

## 6. MCP 전송 방식

`[해석]` MCP(Model Context Protocol)는 두 가지 전송 방식을 지원한다.

- **로컬(stdio)**: 클라이언트가 서버를 자식 프로세스로 직접 실행한다. 내
  컴퓨팅 자원을 쓰므로, 무턱대고 여러 서버를 동시에 연결해두는 것은 비용이다.
- **원격(Streamable HTTP)**: URL로 원격 서버에 연결한다. 여러 클라이언트가
  하나의 서버를 공유할 수 있다.

`[해석]` 실무에서는 로컬(stdio) 연결이 더 흔하다. 연결해두고 쓰지 않는
서버는 꺼두는 것이 리소스 관리 측면에서 낫다.

## 7. Kiro의 steering·skills (참고)

`[해석]` 코딩 에이전트(Kiro)를 쓸 때 활용할 수 있는 두 가지 확장 지점.

- **steering**: 항상 또는 조건부로 로드되는 규칙 파일. Claude Code의
  `CLAUDE.md`와 같은 역할이다.
- **skills**: 필요할 때만 로드되는 절차서. 예를 들어 "이 라이브러리가 최신
  버전 문법을 쓰고 있는지" 같은 팩트체크 절차를 스킬로 만들어 둘 수 있다.

## 핵심 요약

1. 경로가 고정되면 체인, 경로가 상황마다 달라지면 에이전트.
2. 에이전트 = Model + 하네스(Tools·Memory·Guardrails·Context·Orchestration).
3. 자율성 3단계 — AI Assistant(사람이 실행) → AI Agent(승인 게이트 필요) →
   Agentic AI(시스템 수준 자율).
4. ReAct는 적응력, ReWoo는 토큰 효율 — HotpotQA 기준 5배 차이(`[문서]`).
5. 도구는 단일 책임 + 구조적 description, MCP는 stdio(로컬)와 Streamable
   HTTP(원격) 두 전송 방식.

## 확인하지 못한 것

- "함수를 이제는 모델이 만들고 호출도 한다"는 표현은 실습에서 확인한 것이
 아니라 강의 중 일반화다. 실제로는 모델이 **기존에 정의된 도구를 선택·호출**
 하는 것이 표준 패턴이고, 도구를 모델이 새로 만들어내는 것은 별도 논의
 (코드 생성·실행 도구)에 해당한다. 이 노트는 강의 표현을 그대로 두되 이
 구분을 밝혀 둔다.
