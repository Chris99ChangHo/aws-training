# Agents — 벤더 독립 에이전트 계열

AWS가 만들어 제공하는 에이전트를 해체해서, **특정 클라우드 벤더에도 특정 AI
도구(하네스)에도 종속되지 않게** 재구현한 작업물이다.

이 폴더는 상위의 과정 폴더들과 성격이 다르다.

| 축 | 내용 | 성격 |
|---|---|---|
| 과정 폴더 (`generative-ai-essentials/` 등) | AWS 오프라인 수업 이론·실습 | **학습 기록** — 시간순, 과정별 |
| **`agents/`** | AWS 에이전트 해체·재구현 | **작업물** — 재사용 가능한 계열 |

## 에이전트 목록

| 에이전트 | 원본 | 상태 | 내용 |
|---|---|---|---|
| [`security/`](./security) | AWS Security Agent | 동작 (테스트 173) | STRIDE 위협 모델링, SAST/SCA/DAST, SARIF 결정론적 게이트 |
| [`devops/`](./devops) | AWS DevOps Agent | 동작 (테스트 64, 어댑터 미구현) | IaC·컨테이너·파이프라인 린트, "plan은 되고 apply는 안 된다" 가드 |

## 공유 코드

| 위치 | 내용 | 추출 시점 |
|---|---|---|
| [`core/gate/`](./core/gate) | `merge_sarif.py`, `gate.py` — SARIF 병합과 결정론적 판정 | devops가 같은 게이트를 필요로 한 시점. 원칙 3의 "소비자 2개" 충족 |

공유 게이트는 자기 위치로 어느 에이전트를 위해 도는지 알 수 없으므로
`AGENT_ROOT`로 정체성을 받는다. 이 결함은 추출이 드러냈다 — 옮기기 전에는
`__file__` 기준으로 리포트 디렉토리와 manifest를 찾고 있었다.

## 계열 공통 설계 원칙

에이전트를 하나 더 만들 때 지킬 것들이다. 전부 `security/`에서 실제로 겪고
검증한 내용이다. 근거는 각 에이전트의 README 트러블슈팅에 있다.

### 1. 종속되는 층이 두 개다

| 층 | 없애는 방법 |
|---|---|
| 클라우드 벤더 종속 | 오픈소스 도구 + 개방 표준(SARIF 등) |
| **하네스 종속** | 중립 소스 1벌 → 하네스별 어댑터 **생성** |

두 번째가 더 끈질기다. "Kiro 대신 Claude Code"는 종속 대상만 바꾸는 거래다.
경계를 하네스 **바깥에** 그어야 한다.

### 2. 어댑터는 손으로 쓰지 않고 생성한다

손으로 쓴 설정 파일이 2개가 되는 순간 갈라진다. 중립 소스(프롬프트 +
manifest)에서 생성하고, `--check`로 CI에서 드리프트를 잡는다.

### 3. 소비자가 2개 이상일 때만 추상화한다

`security/`에서 하네스가 2개일 때는 추상화가 잘 된 줄 알았다. **3번째(Codex)를
붙이자 보안 구멍이 드러났다** — 파일 읽기 도구가 훅을 우회하고 있었다.
2개로는 "원래 이런 건가"와 "내가 놓친 건가"를 구분할 수 없다.

같은 이유로 이 폴더의 `core/`도 **두 번째 에이전트가 실제로 생긴 뒤에**
추출한다. 아래 §이음새 참고.

### 4. 강제 지점은 진입 경로 수만큼, 규칙은 항상 하나

MCP 도구 호출은 쉘 명령이 아니라서 PreToolUse 훅이 보지 못한다. 통제를 훅에만
두면 에이전트가 MCP를 쓰는 순간 사라진다. 두 곳에서 강제하되 규칙은 한 파일에
둔다(`security/scanners/_scope_lib.sh`).

### 5. 판정을 LLM에 맡기지 않는다

빌드를 막을지 말지는 파일에서 숫자를 읽어 결정한다. 같은 입력에 같은 답이
나오고, 감사 가능하고, 구독이 없어도 동작한다.

### 6. 종료 코드로 "못 했다"와 "문제 없다"를 구분한다

| 코드 | 뜻 |
|---|---|
| 0 | 실행 완료, 문제 없음 |
| 1 | 실행 완료, **발견 있음** |
| 2 | 거부 (권한 경계 위반) |
| 3 | **도구 미설치** |
| 4 | 실행 실패 |

3번을 0번과 섞으면 도구가 없는 상태가 "깨끗함"으로 보고된다. 실제로 게이트가
빈 리포트를 통과 처리하는 결함이 독립 감사에서 나왔다.

### 7. 만든 사람이 아닌 검토자에게 감사받는다

`security/`는 테스트 91개가 전부 통과한 상태에서 독립 감사를 받았고 **결함
8개(Critical 2)** 가 나왔다. 자기 검증으로는 안 보인다.

### 8. 검증 못 한 것을 문서에 남긴다

"됐다"만 적힌 문서는 근거가 없다. 각 에이전트 README에 "검증하지 못한 것"
표를 유지한다.

## 이음새 — Phase 2에서 `core/`로 올릴 후보

`security/`를 실측 분류한 결과다. DevOps 에이전트를 만들 때 **폴더를 복사하면
약 80%가 중복된다.** 그래서 그 시점에 추출한다. 지금 미리 하지 않는 이유는
위 원칙 3이다.

| 분류 | 줄 수 | 비중 | 해당 파일 |
|---|---|---|---|
| **완전 범용** | 747 | 33% | `adapters/build.py`, `scanners/_lib.sh`, `scanners/preflight.sh` |
| **범용 골격 + 특화 내용** | 1,028 | 46% | `mcp/server.py`, `gate/gate.py`, `gate/merge_sarif.py` |
| **보안 특화** | 472 | 21% | `agent/SYSTEM_PROMPT.md`, `scanners/_scope_lib.sh`, `scanners/run_{sast,sca,dast}.sh` |

여기서 "범용"은 **도메인 축**이다 — DevOps 에이전트가 그대로 쓸 수 있는가.
하네스 축과 혼동하면 안 된다. `adapters/build.py`는 도메인 축에서는 완전
범용이지만(어떤 에이전트든 어댑터가 필요하다) 하네스 축에서는 317줄이
종속이다. 두 축이 직교한다.

`scanners/guard_scope.sh`(417줄)는 내부가 갈린다.

| 구간 | 줄 수 | 성격 |
|---|---|---|
| §1–3 페이로드 파싱 · 구조/카테고리 차단 · 자격증명 | 291 | **범용** — `rm -rf`는 보안 문제가 아니라 그냥 위험한 명령 |
| §4 DAST 타겟 스코프 검증 | 126 | 보안 특화 |

### Phase 2 착수 조건

devops 에이전트가 생겨 `core/gate/`는 추출했다. 남은 후보의 조건은 아래와 같다.

- `adapters/build.py`는 출력 파일명이 하드코딩되어 있다. 공유하려면 manifest의
  에이전트 이름에서 파생시키는 리팩토링이 필요하다. **devops를 붙이며 추가
  제약이 드러났다** — `.claude/settings.json`과 `.codex/config.toml`은 프로젝트
  단위 파일이라 에이전트별로 생성하면 두 에이전트가 서로 덮어쓴다. 생성기가
  에이전트 단위 출력과 프로젝트 단위 출력을 분리해야 한다.
- `scanners/_lib.sh`는 devops가 사본을 갖고 있다. 공유하려면 `SEC_REPORT_DIR`을
  중립 이름으로 개명해야 하고, 그 변수는 5개 파일 8곳에 있다.
- `guard_scope.sh`의 §1–3(페이로드 파싱·자격증명·구조 금지)도 devops의
  `guard_infra.sh`에 사본이 있다. 추출이 맞지만 그 파일은 100개 행동 테스트를
  지고 있어 새 에이전트 추가와 같은 작업에 묶지 않았다.
- `mcp/server.py`는 골격과 도구 정의를 분리해야 공유할 수 있다. devops는 아직
  MCP 서버가 없다.
